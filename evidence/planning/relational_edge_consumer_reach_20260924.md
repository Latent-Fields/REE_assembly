## 2. Type vs collapsed, per relation (Question 2)

- **A (latent proximity), C (shared event), D (shared goal/valence):** never reach any consumer at all, typed or collapsed -- the dump methods are sinks with no reader. The question "does the consumer see the typed version" does not arise because there is no consumer.
- **E (causal/outcome):** reaches a consumer, but **only the collapsed scalar.** `StalenessAccumulator.integrate()` (`staleness_accumulator.py:86`) computes a genuine per-broadcast, per-anchor `attribution_weight * strength` increment (non-uniform under `attribution_mode="stream_overlap"`, per the spike) and folds it into `self._staleness[region_key]` in the **same loop iteration** (`staleness_accumulator.py:135-150`, `self._staleness[region_key] = nxt` immediately after the log line). `edge_log()`'s docstring states this plainly: "the only way to recover per-broadcast, per-anchor credit -- `snapshot()`/`get_stats()` expose only the post-leak, post-accumulation region aggregate" (`staleness_accumulator.py:199-207`). Every native reader (`ghost_goal_bank.py:620-637`, `module.py:3887-4245`) calls `snapshot()`/`get()`/`lookup_by_anchor_key()` -- the collapsed form, confirmed by the grep in Section 0. So E is the one type with a genuine live-consumer chain, and that chain is architecturally blind to the type distinction (it doesn't even see "this credit came from a broadcast" vs. any other source -- it sees only the accumulated float).
- **SD-097 "enables" (not one of A-F):** reaches a consumer typed, in the trivial sense that the read is edge-weight-aware and existence-gated -- but there is only one type registered (`possibility_topology.py:174-192`, `default_registry()` docstring: "a fresh registry carrying only the relation SD-097 ships"). `RelationRegistry` (`possibility_topology.py:129-171`) is written to support more than one relation (`register()`, `names()`), and `_admit_relational_successors` parametrises on `relation = str(getattr(tcfg, "seed_relation", "enables"))` (`ghost_goal_bank.py:492` per the earlier grep) -- but nothing currently registers or reads a second relation. So there is no live case where the SAME consumer call reads two types and could be shown to depend on which one it got.

## 3. Verdict (Question 3): NOT RUNNABLE today

A typed-vs-collapsed discrimination needs one consumer whose **output depends on which edge type it reads**, so that permuting one type (holding its marginal distribution and the other types fixed) changes the output while permuting a different type, or none, does not. That requires the consumer to read >=2 types side by side. No such consumer exists:

- The four MECH-468 types (A/C/D/E-as-typed) reach **zero** consumers (Section 1).
- The one type that does reach a consumer (SD-097 `enables`) is the **only** type that consumer reads -- permuting it against nothing is an existence/ablation test (does the edge matter at all), not a type-discrimination test. It cannot disagree with a "collapsed" alternative because there is nothing else to collapse it with.
- E's collapsed staleness scalar is read, but the typed version that would need to be compared against it is provably destroyed before any reader sees it (`staleness_accumulator.py:135-150`, confirmed above) -- there is no live typed E to permute in the first place, only the logged-and-discarded-by-default `edge_log()`.

**Missing consumer, named precisely:** a native valuation/selection consumer that reads **two or more distinct relational edge types over the same anchor pair simultaneously**, with type-differentiated scoring (i.e. its output can be shown to depend on *which* type an edge carries, not merely whether an edge exists). None of `GhostGoalBank.rank()`, `_admit_relational_successors()`, `StalenessAccumulator`'s readers, or `e3_selector.py` do this. The nearest scaffolding is `GhostGoalBank._admit_relational_successors()` (`ghost_goal_bank.py:446-609`) -- it already has a `relation` parameter and a per-edge weight read; it would need (a) a second relation type actually written to the topology (the closest candidate is turning D's already-computed `goal_match` into a thresholded "shares_goal" edge, which the spike already scoped as the cheap tier) and (b) type-conditioned weighting inside the admission loop (currently `relation_weight` is a single scalar applied uniformly to whichever `relation` string is passed in, not per-type).

**Work-graph debt vocabulary classification: `complicated (buildable)`.** This is not a probe-gated unknown -- the mechanism, the call site, and the data needed to build a second edge type (D's goal_match values are already computed and discarded at `ghost_goal_bank.py:340-354`) are all known today; it is direct engineering on an existing, proven pattern (SD-097 already demonstrates one edge type reaching a native consumer and changing trajectory membership). This mirrors MECH-468's own claims.yaml tag on the same subject ("complicated (buildable)").

**Recording-only dumps are D0/D1 instrumentation, not evidence.** The A/C/D/E dump methods populate structures that a future analysis script could read offline, but nothing in the closed loop (`observation -> representation -> prediction -> evaluation -> commitment -> action`) is different with `record_relational_snapshot`/`record_relational_components`/`record_edge_log` True vs False -- confirmed bit-identical by the commit's own contract test name and by the zero-production-caller grep here. A MECH-468/469 experiment run today against only these dumps would be scoring a log file against itself, not testing whether topology changes behaviour.

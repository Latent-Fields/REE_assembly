## 1. Reproduction and method

### 1.1 Set reproduction

`validate_recording.check_criteria_thresholds` (ree-v3) run over
`REE_assembly/evidence/experiments/*.json` (1071 files scanned) returned, for `outcome == "PASS"`:
53 none_rederivable, 0 partial, 2 combination_rule_only, 5 criteria_unrecorded. Keeping
none_rederivable plus partial gives **53 manifests over 40 distinct claims -- the flag's figures
reproduce exactly.**

The count carrying `evidence_direction: supports` is now **34, not 35**. The drift is explained:
the later-emitted V3-EXQ-171 copy (20260330T070404Z) was set to `superseded` today by
governance-flags-20260923b (REE_assembly 7b340c38aa7, GFLAG-0245). `claim_evidence.v1.json`
has not been rebuilt since, so it still scores that copy as MECH-033 `supports` (§5).

### 1.2 Triage order: load-bearingness first

Every manifest was joined to its `claim_evidence.v1.json` entries (direction, `scoring_excluded`)
and to its claims' genuine-experimental counts:

- **Tier 1:** `supports` entries that count toward the posterior, with no `scoring_excluded`
  (29 manifests). Within this tier, priority went to claims where the run is the claim's only
  genuine experimental entry.
- **Tier 2:** `supports` in the manifest or the index, but already scoring-excluded,
  superseded, or claim-free (8: 153, 244b, 500, 500a, 890, 917, 918a, the 171 duplicate).
- **Tier 3:** non_contributory, diagnostic or null direction (16).

All 53 were audited; the tiering set the order and the depth of verification.

### 1.3 Audit procedure

1. **First pass:** 9 parallel read-only audits, one per batch. For every manifest the driver
   was read **at its run-time commit**, using the last commit at or before the manifest
   timestamp, or the first commit where every commit postdates the run by minutes (common in
   March-April 2026; each audit says which it used). Substrate and env code was also read at
   run time where the argument depends on it. Each load-bearing criterion was classified
   attainable / unattainable / entailed / degenerate / undeterminable, with code line refs and
   the measured magnitudes, and each manifest was then classified.
2. **Calibration:** re-derived V3-EXQ-936a blind. The result was 7,901x short on the mean and
   4,044x on the best seed, matching `failure_autopsy_V3-EXQ-936a_2026-08-30`.
3. **Adversarial verification:** every bucket A call (the ones that would move a claim) went to
   5 independent verifiers, each told to *refute* it. They looked for missed stochastic or
   training paths, config values that differ at run time, over-strong implications
   ("A makes B likely" presented as "A entails B"), and mis-identified gating.
   - This pass **caught one over-call in substance.** V3-EXQ-598c's C3 is *not* entailed by the
     readiness precondition: the two use different statistics (last sample vs 12-sample mean),
     and rule_state also takes in z_delta. A 0.26 bar would have failed seed 2. The direction
     proposal survives, but on different grounds (the run is a wiring probe; its `weakens`
     signature is unreachable).
   - It also **narrowed** V3-EXQ-501, 517c/d, 888 and the MECH-033 label (C1 is "attainable but
     non-discriminative", not strictly entailed).
   - For the MECH-033 family the verifier replayed the env at both run-time commits with each
     constant action. All 11 recorded chain cells match a single constant move to 1e-12 in
     harm rate, with the exact event count, and the random-arm counts reproduce exactly
     (4179/4137/4125/4205). That replay is a scratch check, not evidence.

Bucket B and C calls were first-pass only, except the V3-EXQ-158 C3 leg, which was verified.
They move no claim, so they carry less risk.

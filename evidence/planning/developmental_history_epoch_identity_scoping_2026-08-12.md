## 1. The question, made precise

The parent doc's framing — "is enabling a mechanism only at evaluation time scientifically equivalent to the organism having developed with it present throughout" — bundles two distinct mechanisms of non-equivalence that need separating, because they have different implications for what a schema would need to record:

- **(a) Weight-shaping.** If a mechanism participates in gradient-based learning (directly, by updating weights, or indirectly, by changing what data the agent's other learned components see during training), then "developed with it present" and "flipped on at eval" are not two settings of the same organism — they are two different sets of trained weights. There is no coherent sense in which enabling the mechanism at eval alone reproduces what training-with-it-present would have produced, because the weights were never shaped by it.
- **(b) State cold-start.** If a mechanism maintains its own persistent state across time (an EMA, a running count, an accumulator) that is *separate from* the trained weights, then a fresh instance enabled only at eval starts that state empty. The organism's weights may be identical either way, but the mechanism's own accumulated content is not — it needs however many ticks the state's own time-constant requires to reach anything resembling what it would hold under continuous operation.

Both are real, and a given mechanism can exhibit either, both, or (in principle) neither. Below, three of the parent doc's grounding mechanisms are read against implementation to classify which.

## 2. Survey: which REE-v3 mechanisms are plausibly history-dependent

### Tier A — literal weight-shaping (training-time gradient updates)

**Sleep consolidation (`SD-017`/`MECH-120`, `sws_enabled`/`rem_enabled`/`shy_enabled`).** `ree_core/sleep/cross_module_consolidation.py:179-180` calls `loss.backward()` then `opt.step()` — sleep is not a readout or a gate, it is an offline training pass that updates model weights from replayed experience. "Flip sleep on only at eval" is close to *incoherent* as a concept for this mechanism: standard evaluation protocol holds weights frozen, but sleep's entire function is to change weights. The only sensible reading of "enable at eval" for a weight-updating mechanism is "run consolidation during the eval window too," which is not evaluation in the usual sense at all — it is continued training under a different name. This is the cleanest possible case of Tier A, and the parent doc's intuition about sleep was right for a mechanistic reason it did not itself trace to code.

Consequence: for Tier A mechanisms, "developmental configuration" is not an optional refinement of "test-time configuration" — the two questions are close to non-comparable, and a canonical profile that records only a current-value config dict (as `manifest_core.py`'s `config` field does today, confirmed below) cannot even express the distinction, let alone answer it.

### Tier B — persistent accumulator state, no gradient updates

**MECH-304 conditioned safety store (`use_conditioned_safety_store`).** `ree_core/safety/conditioned_safety_store.py` is explicit in its own docstring: "Non-trainable. Pure arithmetic. No nn.Module inheritance." It maintains `self._prototype`, an EMA of `z_world` at MECH-302 relief-completion event ticks (`ema_alpha=0.1` default), initialised to all-zero, plus a per-step L2 decay (`decay_rate=0.001`) that forgets in the *absence* of reinforcement. A fresh instance enabled only at eval has `_prototype = [0.0] * world_dim` — no cue-safety association has ever been encoded. Whatever safety-prediction quality the mechanism would show under continuous operation (built from however many MECH-302 events occurred across the organism's whole history) is categorically unavailable to a cold-started instance within a single eval episode; the EMA time-constant (`alpha=0.1`, i.e. ~10-tick half-life-ish) means it partially recovers within an eval episode long enough to accumulate several events, but starts from nothing.

This is Tier B, not Tier A: the store holds no trainable parameters, so there is no weight-shaping question — but "developed with it present" vs. "flipped on at eval" are still not equivalent, for a different, state-cold-start reason. A canonical-profile schema that recorded only "was the flag True or False" for this mechanism would silently conflate "prototype built over N training episodes" with "prototype built over the last few eval ticks" — two very different operating points reported under the identical flag value.

### Tier C — gating/arbitration over a learned component, no state of its own

**MECH-090 beta-gate triad (`beta_gate_bistable`, `use_commit_readiness_gate`, `use_vs_commit_release`, `use_coalition_controller`, ...).** `ree_core/heartbeat/beta_gate.py`'s `BetaGate` carries per-episode counters (`_propagation_count`, `_hold_count`, `_n_elevation_admitted`, etc.) that are documented as "Cleared on reset()" — i.e. the gate's *own* state does not persist across the organism's developmental history the way MECH-304's EMA does; it is episode-scoped bookkeeping. But the gate's function is to suppress propagation of E3's policy state to action selection during committed sequences — it modulates what a *trained, weight-bearing* component (E3) is allowed to express, moment to moment. If MECH-090 is off throughout training, E3's weights were shaped by a training distribution in which propagation was never held — the network never had to learn to produce a coherent policy under "my output is about to be suppressed for N ticks." Flipping the gate on only at eval exposes those weights to a held-state regime they were never trained under: a distributional-shift argument, not a state-cold-start argument. The mechanism itself has no memory, but what it gates does.

This is the subtlest of the three: MECH-090's *own* state genuinely resets every episode, so a narrow reading of "does this mechanism have history-dependent behaviour" could wrongly say no. The dependence is real but indirect — it lives in the interaction between the gate and E3's already-trained weights, not in the gate's internals.

### Is Tier D (genuinely test-time-safe) actually populated?

A quick scan across the modules backing the parent doc's §14 HIGH/MEDIUM-confidence candidate list (`use_harm_stream`, `use_resource_proximity_head`, `use_per_stream_vs`, `use_lateral_pfc_analog`, `use_dacc`, `use_salience_coordinator`, `use_structured_curiosity`, `use_event_classifier`, `use_pcc_analog`/`use_aic_analog`, `use_amygdala_analog`) finds every one of them wired into `agent.py` and backed by a stateful predictor/analog module (`e1_deep.py`, `e3_selector.py`, `anchor_set.py`, `bla.py`, `cea.py`, etc.) — none is a pure stateless transform sitting outside the training loop. This is not a coincidence of what was sampled: the parent doc's own §3 methodology explicitly *excluded* debug/log/instrumentation-named flags when building its "scientifically meaningful" candidate set. A flag that neither accumulates state nor influences the action-selection path an agent's own weights are trained against would not have behavioural consequences worth calling "scientifically meaningful" in the first place — meaningfulness and history-dependence are not independent properties here, they are close to the same property viewed from two directions. So the honest expectation is that **Tier D is sparsely populated among exactly the flags a canonical profile would care about**, not because every flag was individually checked, but because the selection criterion that makes a flag profile-worthy (§9 of the parent doc: corpus enablement, behavioural exercise) is close to the same criterion that makes it history-dependent. This reframes the question from "which of the 341 default-off flags need developmental tracking" (a large, expensive-to-individually-verify set) to "which of the ~132 claim-linked, profile-candidate flags are exempt" (a smaller set, and the presumption runs the other way — a flag is presumed Tier A/B/C unless shown otherwise, not the reverse).

### MECH-302/303 (not directly inspected here)

`use_suffering_derivative_comparator` and `use_contextual_safety_terrain` were not read at implementation level in this pass (budget); given they sit in the same safety-triad family and interact directly with MECH-304's store (§14 of the parent doc already flags this triad as MEDIUM confidence, conditional on the open MECH-303 sourcing-mode chip), the working assumption should be Tier B or C pending an actual read, not Tier D by default — do not treat their absence from this survey as evidence of test-time safety.

## 3. Have any existing V3 experiments already tested this distinction?

**No.** Searched `ree-v3/experiments/` for (a) any driver toggling a config flag mid-script on an already-constructed agent/config object for the sleep, MECH-090, or MECH-302/303/304 flag names, and (b) naming conventions suggestive of the design (`eval_only`, `test_time_only`, `enable_at_eval`, `cold_start`, `warm_start`, `frozen`, `zero_shot`, `checkpoint`-load-then-flag-flip). Three near-misses, each confirmed to test a different question:

- **`v3_exq_819a_mech457_inv088_zworld_trained_vs_random_gatefix.py`** — despite the "trained_vs_random" name, this compares a *prediction-pretrained* z_world encoder against a *frozen random-projection* encoder, with the flag's effective state constant across the entire run in both arms (no phase where the encoder is off during a "training" stretch and on only for "eval"). It is a representation-quality question (does pretraining the encoder help), not a mechanism-presence-during-development question. Genuinely adjacent, not a match.
- **`v3_exq_538_sd049_phase2_with_sleep.py`** / **`538a`** — "Phase 2" refers to SD-049's own curriculum stage, not a train/eval split; all three arms (sleep off / SD-017-only / full Phase-A scaffolding) run sleep at the stated setting for the arm's entire episode budget. A whole-run ablation, not a within-run transition.
- **MECH-457 "cold-start floor" cluster** (`v3_exq_765`/`769`/`780`/`772`, ref'd in prior-session memory as "4 axes eliminated; 781 confound") — this is about bootstrap *competence* (can an agent explore effectively before it has learned anything at all), a genuinely different cold-start question from "was mechanism X active during this agent's development." Worth noting as the closest existing *methodological* precedent in this codebase for reasoning carefully about what "no prior exposure" means operationally, but it does not test our question and should not be cited as if it did.

No `train-without → freeze weights → flip-on → eval` or `train-without → continue-training-with-flag-on → eval-at-various-checkpoints` design exists in the corpus for any of the three example mechanism families. This is a genuine, currently-empty gap in the evidence base, not merely an unasked question in the abstract.

## 4. Recommendation

**Yes, this should become a formal (but narrowly-scoped) dimension of canonical-profile/epoch identity — not a blanket requirement across every default-off flag.**

Reasoning:

- §2 found the distinction is not confined to the three named examples; it plausibly generalizes across most of the profile-candidate surface (Tiers A/B/C), because meaningfulness and history-dependence share a root cause here (behavioural influence during training). A canonical profile — whose entire purpose (per the parent doc §8) is to name *which curated organism* a run used — would be silently wrong for any Tier A/B/C mechanism if "organism used profile P" is recorded identically regardless of whether P's flags were present from the start of training or switched on afterward.
- But requiring a full developmental-history schema for **every** default-off field (currently 341, growing) is disproportionate: most of that surface is either Tier D-by-elimination (excluded from "meaningful" already) or governed by deliberate holds (§4a of the parent doc — `use_differentiable_cem` and siblings) where the question is moot because the flag isn't being admitted to a profile at all yet.
- The right scope is: **any flag being considered for admission to a canonical profile** (the parent doc's §9 admission criteria) picks up one additional, cheap admission question — "was this flag's config-effective value constant across the qualification run's full training history, or did it change partway?" — answered by the qualification battery (§12 of the parent doc) the profile mechanism already needs to build, not by a new mechanism.

### Minimal schema-extension sketch (not built; for the eventual profile mechanism's designer)

Two options, cheapest first:

1. **Two-point diff, reusing existing machinery.** `manifest_core.py`'s `config` field (confirmed: a single `dict(config)` snapshot, current-value-only, no history — `experiments/_lib/manifest_core.py:1096`) already records the *end-state* config. Add one sibling field, `config_at_run_start` (or reuse `arm_fingerprint.py`'s existing `compute_substrate_hash`/`config_slice` machinery to hash it, mirroring how OFF/ON arms are already fingerprinted for reuse-eligibility): record the effective config at episode 0 alongside the config at manifest-write time. Equality of the two hashes is the common case (flag constant throughout — the vast majority of today's corpus) and needs no further action. Inequality is the signal that a run mixed developmental regimes, and should route to whatever cross-epoch-comparison annotation convention the parent doc's §11 already proposes for `canonical_profile` boundaries generally — this is the same shape of problem (comparing across a configuration boundary within one report) applied at run-internal rather than run-to-run granularity.
2. **Full transition log** (only if #1 proves insufficient in practice): a `config_transitions` list of `{step_or_episode, field, old_value, new_value}` entries, written whenever a driver script mutates `cfg.<flag>` after agent construction. Higher fidelity, meaningfully more implementation and governance burden (validation, storage growth across ~1,300+ scripts), and nothing in the current corpus (§3) demonstrates a need for more than a single transition point per run — drivers that toggle flags mid-script today do so at most once (train-phase config → eval-phase config), not in a multi-stage curriculum of flag changes. Start with #1; escalate only if a real experiment design needs more than one transition point.

Either option is plumbing on top of machinery §2 of the parent doc already confirms exists (`arm_fingerprint`'s hash/slice pattern, `manifest_core`'s config recording) — this is not a new subsystem, consistent with the parent doc's general finding that the profile-identity gap is an integration problem, not a from-scratch build.

## 5. Explicit statement on "does this matter for REE-v3's current mechanisms"

This is not a foregone conclusion answered "yes" by fiat — stated explicitly per the task's own instruction:

- For the specific three families the parent doc named (sleep, MECH-090, MECH-302/303/304), the answer is **yes, it matters**, and §2 traces *why* at the implementation level rather than asserting it: one is literal weight-shaping (sleep), one is state cold-start (MECH-304), one is trained-weight distributional shift under a gate (MECH-090).
- The generalization in §4 — that this plausibly extends to most of the profile-candidate surface — is a **prediction from the shared root cause found in §2**, not a per-flag verification; MECH-302/303 were explicitly not checked (§2 closing note) and neither was any HIGH-confidence flag beyond the modules-backing-them grep in §2's Tier-D discussion. Treat "plausibly Tier A/B/C" as the working default for admission purposes, not as an established fact for any specific untested flag.
- The one place the answer plausibly is "does not matter" is the excluded-by-construction Tier D — debug/log/instrumentation flags and any flag that is provably both stateless and non-participating in the training-time action-selection path. §2 argues this set is close to disjoint from the profile-candidate set by the parent doc's own selection methodology, but that is an argument from selection criteria, not an exhaustive check, and a genuine counter-example may exist and simply wasn't found in this pass's budget.

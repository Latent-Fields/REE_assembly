**CANDIDATE-STALE vs RETEST-DUE -- these are NOT the same finding.** CANDIDATE-STALE means the substrate/campaign is EXHAUSTED (assembly_status ran_exhausted_for_substrate / ran_non_contributory / exhausted) -- the retest already ran its course and the claims.yaml flag is genuine drift, matching the SD-034/GAP-4 incident this tool was built to catch. RETEST-DUE means the linked node's plain `status` turned done/deferred -- per serve.py's own retest-prompt logic this means the substrate just landed and the retest is now ACTIONABLE, which is the flag correctly doing its job, not a bug. Do not read RETEST-DUE entries as errors to fix; they are a todo list, not a defect list.

UNLINKED/UNDETERMINED are NOT clean -- they are claims this tool could not safely adjudicate (no *_plan.md node names them via unblocks_claims, or the dates needed to order claim-vs-substrate are missing). Do not read the CANDIDATE-STALE count alone as full coverage; the UNLINKED+UNDETERMINED count is the un-audited population and should be read alongside it, not folded into "0 stale".

**CANDIDATE-STALE confidence caveat**: a finding's `confidence` is `high` when its narrowest driving node's `unblocks_claims` list has <=8 entries (a claim-specific gate, like the real SD-034/GAP-4 incident's 6-claim node) and `low_broad_umbrella_node` when every driving node is a large shared campaign-level node (12-20+ claims). A `low_broad_umbrella_node` finding is real evidence the CAMPAIGN hit a terminal state after the claim was last touched, but says less about that ONE claim individually -- treat it as "worth a governance look", not as pre-adjudicated.

This tool does NOT edit claims.yaml, substrate_queue.json, or any *_plan.md. Adjudicating a flagged claim (clearing the flag, updating plan-doc prose) is /governance's job.

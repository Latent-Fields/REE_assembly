# Object files: the founding construct for MECH-045

Kahneman, Treisman and Gibbs (1992) is the paper MECH-045 is named after. They asked a deceptively simple question: when a feature appears on an object and then, a moment later, another feature appears, what makes the visual system treat the second as *a new state of the same thing* rather than a separate event? Their answer was the **object file** — a stable, object-specific representation opened when an object is first individuated, into which later features are written and against which later features are matched. The empirical signature is the **object-specific preview benefit**: naming a target letter is faster if it was previewed *on the same object*, and crucially this benefit does **not** transfer to a different object showing the same letter.

What makes this the right grounding — rather than a generic "memory helps" result — is *how* they established sameness. Across experiments the link between preview and target was carried by shared location, by shared **relative position in a moving pattern**, and by **successive appearance in the same moving frame**. In other words, the file follows the object *through motion*, and it does so by spatiotemporal continuity, not by the object's features and not by any symbolic label. This is exactly the three-part demand MECH-045 places on the substrate: bind features **across time and motion**, keyed by an **entity token instance**, **without symbolic/type labels**.

The translation to REE is close to one-for-one at the functional level. The object-specific (not feature-specific, not category-specific) nature of the benefit is the very type-vs-token distinction ARC-080 calls "the first fork": an object file is bound to *this* apple as it moves, not to *apples*. That is the gap between the live SD-057 `IncentiveTokenBank` (keyed by resource type) and what MECH-045 actually requires. The paper motivates a token KEY computed from **spatiotemporal continuity over z_world** with no type tag, and an **attention-gated, capacity-limited** buffer — both of which ARC-006's design constraints already gesture at.

The honest caveats are two. First, the construct has a well-known soft underbelly: later work (Mitroff & Alvarez 2007 and others) showed the preview benefit can in some conditions be carried by **location** alone rather than by a genuine label-free identity token. For REE this is not an academic footnote — it is the precise vacuity hazard. A data-association KEY that quietly collapses to "whatever was in the nearest cell last tick" would reproduce the preview-benefit signature *without ever re-identifying a moved entity*. That is why the pre-registered experiment must carry a non-vacuity precondition that forces the buffer to re-identify an object that has **moved to a new cell** before the persistence test can score. Second, this is human psychophysics over sub-second timescales; it establishes the function REE must reproduce, but it neither prescribes the latent-space algorithm nor speaks to whether z_world at dim=32 is discriminative enough to support it (a question I take up against the 641a ceiling in the design memo). Confidence 0.82: maximal mapping fidelity because it is the construct itself, discounted for the function-not-mechanism gap.
